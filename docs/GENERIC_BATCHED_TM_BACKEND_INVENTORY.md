## Existing dense API and layout

The baseline module exports `BatchedMonomialBasis`, `BatchedPolynomial`, and
`BatchedTaylorModel`.  Polynomial coefficients use
`[batch, output, monomial_slot]`; Taylor-model remainder endpoints use
`[batch, output]`; domains use `[batch, polynomial_variable]`.  The default
dtype is float64 and tensors retain their device.  Public polynomial operations
are add, subtract, scale, affine map, truncated multiply, natural interval
range, point evaluation, component selection, and concatenation.  The Taylor
model adds interval-remainder propagation and a VDP helper.

The complete-total-degree exponent order is deterministic: increasing total
degree, then the recursive lexicographic order generated by assigning each
variable from zero upward.  Sparse `Polynomial` instead sorts exponent tuples
lexicographically.  Conversion therefore must use exponent tuples, never slot
position.

## Coordinate contract observed in the sparse solver

`flowpipe_step_from_tm` starts from two normalized uncertainty variables and
appends physical local time as the final variable.  Consequently the VDP
order-4 segment has `n_vars=3`, `tau_index=2`, and
`comb(3 + 4, 4) = 35` complete-basis slots.  State dimension remains two and
is independent of both batch size and polynomial-variable count.  The local
time domain is `[0,h]`; `TaylorModel.integrate(tau_index)` integrates in
physical time and does not multiply by `h` again.

## Baseline operator findings

- The multiply plan contains all ordered pairs.  Cross products intentionally
  occur twice when algebra requires the two ordered contributions; a
  self-product is therefore correct only if scatter aggregation preserves that
  ordering.
- CPU `scatter_add_` is deterministic for this fixed route.  CUDA reduction
  order may produce last-bit coefficient differences and must be checked by
  containment plus a declared float64 arithmetic tolerance, not assumed bit
  identical.
- Retained multiply coefficients are aggregated by basis slot.  Dropped terms
  are intervalized per route entry, however, whereas sparse `Polynomial`
  combines equal exponents before interval evaluation.  The baseline dense
  remainder is therefore generally wider and is not tightness-equivalent.
- Natural range constructs safeguarded monomial power intervals, multiplies
  them interval-wise, sums term bounds, then applies `nextafter` to the sum.
  Power and interval products are also safeguarded.  This is an algorithmic
  float64 safeguard contract, not a hardware-independent rounding proof.
- Taylor-model multiplication includes all four mathematical parts: retained
  `P*Q`, dropped `P*Q`, `P*J + I*Q`, and `I*J`.
- There is no integration route, cutoff ledger, sparse/dense conversion
  contract, composition route, or basis fingerprint.

## Solver and carry findings

At baseline, `fixed_picard_step_vdp` ignored `order` and returned `self + h*rhs`; both it and
`one_fixed_tm_step_vdp` are Euler aliases.  Existing tests check sampled Euler
containment, not a Taylor/Picard fixed point.  The demo repeats the same Euler
kernel and is not a reachability solver.

At baseline, `recenter_rescale()` returned `self`, which silently prevented a correct
normalized cross-step map.  The production sparse solver already supplies the
scheduler, target-remainder subset validation, raw endpoint, segment tube,
adaptive rejection/retry, normalized insertion, right-map composition, and
status protocol.  A first integration lane can therefore use dense Picard,
dense remainder validation, and a single tested conversion at each segment
boundary while retaining the sparse outer normalized-insertion scheduler.  It
must be identified as `hybrid_dense_core`; conversion may not occur in a
Picard or validation inner loop.

The production functions requiring a backend choice are polynomial Picard,
candidate construction, remainder self-map evaluation, cutoff, and endpoint
construction.  Adaptive scheduling and `FlowpipeSegment` status/output fields
can be reused.  Full-dense qualification additionally requires replacing the
normalized insertion/right-map boundary path.

## Historical evidence and read-only references

Committed sparse evidence places natural target-subset rejection near
`t=6.31729088` for constant right-map centering and near `t=6.39093111` for
range-midpoint centering.  A fresh 300-second run ending near `t=6.05` is a
timeout, not a new mathematical boundary.  The terminal mechanism is growth
in polynomial range/raw remainder until target subset fails; centering alone
did not close it.

The read-only `origin/codex/batched-dense-nncs-gpu` branch contains reusable
generic ideas: grouped dropped exponents, blocked/split natural range kernels,
and synchronized profiling.  Its controller/TORA/NNCS code, Euler rollout,
and synthetic replicated workload are rejected for the plant-only solver.

The Xiangru checkout is read-only.  Immutable exponent support, precomputed
routes, batch-first storage, cached factors, explicit CUDA synchronization, and
leafwise fail-closed status are applicable.  Its TORA RHS, controller period,
fixed state/control dimensions, six-variable compile assumption, and property
machinery are not applicable.

## Required migration invariants

1. Dense/sparse conversion maps by exponent and rejects out-of-basis terms.
2. Every truncation, cutoff, integration overflow, nonlinear remainder product,
   and boundary loss is represented in a named remainder-ledger category.
3. `recenter_rescale()` cannot remain a silent no-op.
4. The dense core uses genuine local-time Picard and an unchanged subset test.
5. Batch, state output, polynomial variables, and local time are independent
   dimensions with explicit shape checks.
6. The first hybrid lane records conversions, device transfers, and sparse
   fallback count; full-dense identity is forbidden until boundary composition
   is dense too.
