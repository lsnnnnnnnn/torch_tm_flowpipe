# Numerical scope, external code and proof relationship

The comparison in this review is about a plant-only polynomial ODE pipeline. It retains useful interval and Taylor-model enclosures but does not have one blanket, end-to-end formal soundness theorem for every path. A local `strict` range or composition result means that specific operator has a stated arithmetic enclosure under stated assumptions; it does not certify all upstream retained-coefficient updates, scheduler choices, or future steps. The main data and provenance are in [results/review](../results/review/), with fixed versions in [the registry](../experiments/review_suite/registry.yaml).

## Five versioned arithmetic/state witnesses

1. **Time substitution.** In an actual production endpoint operation, `P(t)=-1+100t` at the binary64 encoding of `0.01` has exact value `3/144115188075855872`, about `2.0817e-17`. A prior retained-point substitution rounded it to zero with zero remainder; outward-moving that zero by one subnormal ulp could not contain the exact expression. The endpoint-repair path encloses time powers, coefficient products and equal-term sums separately, then charges the difference between the resulting coefficient interval and the retained point polynomial. The [endpoint repair report](endpoint_roundoff_repair/REPORT_PLAIN_CHINESE.md) and [re-evaluation stop record](backend_reevaluation/REPAIR_REUSE_PLAN.md) give the exact oracle and production call. The Xiangru snapshot's tested strict endpoint calls failed on this local input; the saved Huan repair included it. A local correction does not retrospectively certify an older full trajectory.

2. **Integer powers.** For `x=0x1.7d3ecfa658d9bp+9`, exact `Fraction(x)^3` fell outside the old `Interval(x).pow_int(3)` result. [The current regression](../tests/test_range_requests.py) keeps that old failing path as a historical witness and checks that `certified_scalar_power` and the real `RangeRequest` entry contain the exact value. This is a fix at the strict request boundary. It does not make every caller of legacy interval powers automatically safe.

3. **Retained coefficients.** The exact product of two binary64 values named `1.1` differs from the rounded point `1.1*1.1`. The old sparse CPU normal-composition block returned its rounded point coefficient with an almost-zero remainder that missed that difference. The resident composition block propagates directed coefficient intervals and pays the interval polynomial error once at its output; its local error interval includes `[-0,2^-52]` in the recorded witness. [The block contract](resident_tm_block/NUMERICAL_CONTRACT.md) and [regression](../tests/test_resident_tm_block.py) define its actual scope. Enabling that optional block does not repair the default CPU polynomial/Picard path outside it.

4. **History matrices and scale.** The saved repair re-evaluation used exact rational oracles on the old historical matrix witness, a non-unit-scale derivative, and zero-constant affine normalization. The `743f620...` strict production calls passed in CPU/CUDA dense/sparse scope; the `1c16d4...` candidate strict calls failed. The required assets were interval Phi/scalars, matrix products, reciprocal/normalization error and their ownership in current `J`. [The repair reuse plan](backend_reevaluation/REPAIR_REUSE_PLAN.md) separates those known paths from its independent endpoint stopping condition. A missing audit API or refinement ledger is weaker evidence than a concrete exact-value exclusion; the two must not be reported as the same failure class.

5. **Next-step ownership and rollback.** The endpoint repair's two-step actual paths check that the new endpoint substitution charge reaches the next accepted state exactly once: it is neither dropped nor added twice to past history, and a rejected attempt does not mutate the accepted queue. The [carry checks](../artifacts/runs/endpoint_roundoff_repair_20260908/two_step_carry_checks.json) and [error ownership record](../artifacts/runs/endpoint_roundoff_repair_20260908/error_ownership.json) include queue boundary/reset witnesses. The repaired fixed full reruns still reached nominal T10/T20; their all-step relative width changes against the older CPU objects were tiny. This shows that the identified endpoint omission was not the main source of the then-observed width gap. It does not establish unconditional arithmetic correctness for every remaining operation.

## Huan proof: first-hand statement and implementation map

The first-hand [paper source](https://github.com/huanzhang12/flowstar-gpu/blob/d5f0b68fcd36ba5f582733624f074728fe9720d8/docs/paper/main.tex) inspected for this branch is `docs/paper/main.tex` in Huan's clean `d5f0b68fcd36ba5f582733624f074728fe9720d8` engine tree; the saved repair `743f620...` did not change that TeX file. Its Theorem `thm:engine-fpsum` (“A-priori inflated reductions, valid for every evaluation order”) bounds an arbitrary binary-tree dot/reduction by `(2m-1)u Σ|a_i b_i| + mη`, provided all intermediate results are finite and `m u ≤ 1/4`, with IEEE binary64 round-to-nearest and gradual underflow. The preceding lemma attributes the pure-sum any-order ingredient to Rump; the paper also asserts a production startup check for no flush-to-zero. The proof is about an explicitly inflated finite operation under these hypotheses, not arbitrary nonfinite GPU execution. `src/flowstar_gpu/rounding.py::dot_error_bound` and the engine's reduction calls were the checked implementation path; the audit verified 987 finite-hypothesis schedules per device against exact binary rationals. [The proof-contract audit](HUAN_ENGINE_PROOF_CONTRACT_20260826.md) maps this and the elementwise path.

The same TeX's `rem:engine-repro` and symbolic-queue section claim that strict mode charges retained point-coefficient and Phi-product roundoff, while parity mode adopts Flow*'s point trust model. The clean `d5f...` audit found strict final composition GEMM inflation but no complete charge visible in symbolic Phi `torch.einsum` and retained monomial-image products; `determinism.py::enable_determinism` did not assert the claimed no-FTZ precondition. D5 refinement lacked a public proposal/commit/cache freshness ledger, so its ownership could not be mapped fully. These source-to-proof gaps stopped the exact VDP and throughput phases in that historical clean-source audit. This is **not** a failed VDP T10 execution of Huan's engine. The saved strict repair may address some paths, but this review did not re-adopt or complete a new whole-engine proof audit.

The older CROWN-Reach integration contains 450 result records naming unavailable `-dirty` engine revisions. Their base commits alone do not reconstruct the missing patches/untracked state, so those records are not current reproduced performance data. This review does not pack external Huan/Xiangru source, binaries, private notes, tokens, or a proof PDF into our branch. Primary TeX is available from the identified clean engine revision; the older [proof-to-code reports](HUAN_ENGINE_REPRODUCTION_AUDIT_20260826.md) remain versioned secondary mapping. Third-party licenses and attribution are preserved. New long-horizon/throughput runs of the external engine remain **not run**, rather than “observed failure.”
