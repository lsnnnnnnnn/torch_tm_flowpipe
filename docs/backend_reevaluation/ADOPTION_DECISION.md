# 接纳决定

`REPAIR_REUSE_NOT_LOCAL__NO_ADOPTION`

当前候选在两处已知局部包含性检查中失败。旧严格修复版在两例、非单位尺度变体和实际 CPU/CUDA dense/sparse 入口通过，表明确有可复用资产；我们的 CPU 同样通过这些检查。

沿这两处修复的真实调用函数核对前提时，发现独立的端点时间代入漏包：`-1+100*t` 在 binary64(0.01) 的精确值为正，当前严格入口返回零且没有余项。它不经过历史矩阵或归一化。目标第 4、8 节要求第三独立问题出现即停，故未创建修复候选、未移植源码，未开启完整候选时域与性能阶段。这个状态不表示旧资产毫无用处，也不表示已证明某条既有长轨迹漏包。

所有 adoption 门的状态：已知例子的旧修复复查通过；当前候选失败；完整误差所有权未闭合；新候选 T20/T10、逐段四项宽度、Flow* 接近标签、B32/B16 性能与 CPU 吞吐门均未建立。无新版本、模式、设备组合获得采用推荐。原 CPU 默认入口保持不变，不增加 opt-in 外部进程适配器。

后续回到我们自己的主线：保留 CPU 两系统结果与其原有安全边界，优先重用现成 profile，分析 Python 和小张量重复调度的主要成本，再决定通用执行结构的改进。两类已知问题的复现材料已准备好，可由用户交给维护者；本轮不发送、不承诺监控等待。这里不启动新 CUDA 重写、第三个 benchmark 或控制器工程。
