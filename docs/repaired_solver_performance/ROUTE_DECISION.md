下一轮只建议一个主方向：在现有 prepared 执行路径上做一个**包含历史传播的真实 B 维短前缀原型**，测完整步骤吞吐与逐 lane 一致性。本轮没有开展这个实验，也没有因此确定最终 GPU 后端。

本轮减少的是同一步内重复的固定多项式乘积、截断和范围准备。Brusselator 三个代表窗口的整个收紧阶段局部加速为 3.86×、4.23×、4.33×，包含准备及命中检查。优化后的历史处理仍占各窗口 scoped solve 的 51%–56%；VDP 为 41%–45%。这些是窗口诊断占比，并非凭窗口推算出的完整长跑分解。只批量化已经缩短的 replay，不能覆盖主要剩余成本。[分项计时](../../artifacts/runs/repaired_solver_performance_20260908T084224Z/profile_windows.csv)与[cProfile 剩余热点](../../artifacts/runs/repaired_solver_performance_20260908T084224Z/remaining_hotspots.csv)同时保留，区间对象构造中的 Torch 检查时间不能全部解释为 Python 解释器开销。

prepared 的系数、余项和 domain 张量已有 B 维，同一有序操作图可以承载多个 lane；每个 lane 的数值必须独立。当前局部 B2 只检查不同余项及两个计划交错时的隔离。完整求解器的 normal state、SR 队列、停止/拒绝和 scheduler 仍走 Python B1 控制流，尚无完整 batch 能力。下一轮原型必须把历史状态和 lane 活动掩码纳入同一次短前缀测量，不能把逐 lane 循环称为并行 batch。

所缺数据是不同初始盒子的 B2/B8/B32 整步吞吐、内存与准备成本，以及跨队列清空、不同收敛轮数和拒绝情况下，各 lane 对独立 B1 的逐位一致性。先取得这组有限数据，才能判断执行结构是否值得进一步 GPU 化；本轮没有用局部加速代替这些证据。已保存的严格 GPU 引擎仍保留为后续选型候选，此次没有复评它们，也不凭本轮 CPU 结果接纳或否定它们。

即使 CPU 完整时间再减半，与历史 Flow* 的量级差距仍可能很大。CPU 追平 C++ 不是开展 GPU 工作的前提，CPU 局部成功也不等于 GPU 选型完成。下一轮应只交付上述有限 batch 原型的完整成本和等价性结论，不同时开展第三方后端复评或完整 CUDA 开发。
