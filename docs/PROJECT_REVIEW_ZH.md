# 多项式系统可达域：供汇报和合作者讨论的研究综述

这个项目研究一个实际问题：从一小片初始状态出发，程序能否给出 Van der Pol 和 Brusselator 在较长时间里的**全部可能状态范围**，同时让范围不要很快变得宽到失去用途，并缩短完整计算的时间。这里的对象是两个纯多项式微分方程，不包含神经控制器或混合状态跳转。Taylor model（泰勒模型）把可保留的多项式部分和无法精确保留的区间余项一起传播；flowpipe（可达管）包住整段时间，不是单条数值轨迹。

首页主实验都使用原始、没有分割的一个初始盒（B1），固定接受 1,000 步：Van der Pol 的阶数为 4、实际二进制浮点步长为 `0.01`，对应名义 T10；Brusselator 的阶数为 6、步长 `0.02`，对应名义 T20。初始余项半径、截断阈值、历史误差队列容量分别由[冻结配置](../benchmarks/review/fixed_profiles.json)核对。二进制浮点的 `0.01`/`0.02` 不等于精确十进制，因此表中的实际有理数累计时间比名义 10/20 稍大；比较使用的是同一实际编码。另有 Van der Pol 自适应步长 T10 实验，它的步序和固定实验不同，不能把其步数或秒数写进固定对比。

## 当前主结果：走完时域，还要看四种范围

每一步有两种视角：**端点**是这一步结束时的状态范围，**可达管**是这一步整个时间段的状态范围；每种都分别记录 x 和 y。这四通道在所有 1,000 个接受步上完整保存。保存的 CPU 与原生 Flow* 完整模型在本分支用同一个当前严格 CPU 观察算子重新求范围；GPU 包裹范围服务使用实际接受步保存的范围，并检查前后状态连贯。观察方式可比，内部的验证、余项收紧和历史传播算法并不完全相同。[完整上下界数据](../results/review/bounds/curves.csv.gz)、[逐步宽度关系](../results/review/bounds/width_ratios.csv.gz)和[来源记录](../results/review/provenance.json)是下表及图的依据。它们目前来自旧科学运行的完整原始记录，经本分支重新计算；新的代表性运行另列来源。

Van der Pol 即使走完 T10，四通道中位宽度仍比这份 Flow* 对照宽约 17–20%；最后一步差距约 11–13%。这说明“完成”并不等于“同样紧”。GPU 路线与我们的 CPU 参考在这个系统的宽度几乎只差浮点舍入尺度。Brusselator 的四个中位比跨过 1，最后一步四项都略小于 1，而且不同时间步会互换宽窄；给它一个统一的“谁最紧”排名会丢掉实际观察。这里的“严格观察”只指这个范围算子的局部性质，不是整个求解器的形式化正确性证明。

## 为什么旧版会停，以及我们尝试了什么

每一步程序必须检查：给出的余项范围是否足以覆盖这一步可能产生的变化；检查不通过就拒绝并依原合同尝试后续步长。旧 Van der Pol 自适应路径（历史 C2）接受 233 步后停在约 6.714915，伴随 37 次拒绝。这不是崩溃。随后历史 C3 在跨步传播时保留过去误差之间的线性关系，不立刻把所有关系摊成互不相关的区间。在同一历史自适应 T10 合同下，它接受 246 步、拒绝 35 次，走到 T10。

有一份额外的**共同固定 632 步**对照，使“完成与否”以外的宽度变化也能检查：旧 C2 的端点 x/y 宽为 0.278221/0.291864，保留关系的 C3 为 0.188094/0.148209；同轮 Flow* 为 0.153076/0.122296。这个对照支持“保留跨步关系有帮助”的经验结论，但固定 632 步的宽度不能和上面自适应 246 步的运行混成一个实验。C3 是后续算术修复之前的历史版本，不能追认成当前完整证明。原始数值、版本及分开的面板见[机制表](../results/review/mechanisms.csv)和[机制图](../results/review/figures/mechanism_comparisons.svg)。

Brusselator 的旧 SR1000 路径接受 357 步后停止；当时历史误差队列尚未填满，也未触发重置，问题出在本步余项覆盖检查。我们试的是：某个余项已经被接受之后，沿原有收紧映射继续做安全的进一步收紧。历史 C4 在冻结的固定 T20 合同下完成 1,000 步；原生 Flow* 对照也完成。后来的“C5”名称是一份审计包的标签，并没有新算法。可以说已接受余项继续收紧是该历史配置里的关键工程变化，不能说“C5 发明了新方法”，也不能把旧停止归咎于队列溢出。

这些工作复现并工程化了已知的验证传播、Taylor model、历史误差与余项收紧思想。这里的贡献包括受控地发现哪些机制影响时域和宽度、修复具体算术入口、做可复用的范围服务和保留真实失败证据；没有证据支持“首次提出全新数学可达性算法”。[当前求解流程和源码位置](METHOD_AND_CODE_MAP.md)把初始盒、本步候选、余项验证、接受后收紧、端点代入、历史更新到下一步依次对应起来。

## 数值问题：修过哪里，还有哪里不能声称已证明

后续使用精确有理数检查真实浮点调用，找到几处不能只凭“有区间”就放心的反例。第一，端点时间代入 `-1+100*t`，在二进制浮点 `0.01` 处的精确值是 `3/144115188075855872`，旧实现留下零多项式和零余项，漏掉这个值；修复路径分别包住时间幂、乘积、同项相加，并把与保留多项式的差额计入余项。第二，旧 `Interval.pow_int(3)` 对一个实际二进制浮点 x 漏了精确立方；新的严格请求入口使用 `certified_scalar_power` 包住它，但没有悄悄把所有旧调用都宣称安全。第三，旧稀疏复合中的浮点 `1.1*1.1` 保留系数漏掉精确乘积；可选的 resident 复合块在**自己的系数运算边界**计算并支付误差。另有历史矩阵、缩放和“下一步只计一次／拒绝不提交状态”见证。

端点修复后的 CPU 原始 B1 固定完整运行仍完成 T10/T20，与较旧 CPU 保存对象相比，各步宽度变化很小。这说明已定位的端点舍入遗漏不是当时 Van der Pol 较大宽度差的主要来源。它并不能证明其他保留系数运算、验证、队列、调度以及整个求解器都无漏洞。[数值范围和外部代码版本表](NUMERICAL_SCOPE_AND_EXTERNAL_CODE.md)逐条写出反例、修复入口、测试范围及剩余条件；“严格”“通过”“参考”一词都不能自动提升为全程序定理。

## 提速：局部很快，完整流程仍有代价

CPU 两次优化有各自的**完整配对**保存记录，所有接受步的数值对象在本轮各自比较中逐位一致。预先准备余项重复检查材料，使 Van der Pol 711.377→693.657 秒（1.0255 倍）、Brusselator 1991.944→1454.661 秒（1.3694 倍）。按序组织张量范围计算，在**已经启用前一优化**的分母上，使两系统分别 696.164→575.062 秒（1.2106 倍）、1440.102→1121.580 秒（1.2840 倍）。每项每系统只有一次完整基准/候选观察，不能把两个倍率相乘当成一个已验证的产品速度。[配对表](../results/review/cpu_pairings.csv)和[图](../results/review/figures/cpu_pairings.svg)保留每轮分母。

GPU 的差异更明显。离线范围批处理连打包和传输的局部中位倍率约为 4.334/4.339；放回真实 B32×20 在线求解，早期范围服务中位倍率为 1.106/1.113，包裹服务增量仅 1.050/1.037，未达到当轮目标。新的设备驻留系数复合块单独测得 42.314/49.573 倍；放回五次配对的整段 B32×20，GPU 包裹服务与 resident 路线的在线中位差别只有 1.138/1.161 倍，两系统均未达到 1.20 的目标。B32×20 指 32 个**不同的**分盒各走 20 步，总计 640 分盒步，不是原始一个盒走 1,000 步。[GPU 路线表](../results/review/gpu_route.csv)和[局部/在线图](../results/review/figures/gpu_local_vs_online.svg)直观保留了这段落差。

对近似匹配参数的同一 B32×20 工作量，原生 Flow* 每个系统各一次调用为 0.703/8.024 秒；resident 的五次配对中位墙钟为 249.890/355.177 秒，约为前者 355.5/44.3 倍。初始盒、阶数、步长、截断、队列和记录中的 CPU 资源尽量匹配，但 Flow* 不暴露我们的接受后余项收紧、历史重放和原子提交控制，因此这是工程尺度比较，不是相同算法的芯片性能比。[匹配参数和限制表](../results/review/matched_flowstar.csv)保留这个条件。resident 复合默认关闭，目前有小样本和连续前缀范围的证据，**没有**原始 B1 的完整 1,000 步 T10/T20 运行；不能把 B32×20 结果写成那个能力。

## 和 Huan、Xiangru 外部代码及证明的关系

Huan 的原始干净引擎源版本为 `d5f0b68...`，保存的严格修复后代为 `743f620...`；单独审计的 Xiangru 快照是 `1c16d4...`。这是三个不同的版本资产，不是对合作者个人水平的排名。Huan 原论文的第一手 TeX 在该干净版本 `docs/paper/main.tex`。其中任意求值顺序的有限二进制浮点归约上界写为 `(2m-1)u Σ|a_i b_i| + mη`，条件包括舍入到最近、渐进下溢、中间结果有限以及 `m u ≤ 1/4`。保存的审计把局部归约实现与精确有理数见证对应起来；但干净版本里未能完整映射全部保留系数／Phi 乘积误差，也没有找到生产启动对“不开 flush-to-zero”条件的断言，余项提议和提交的新鲜度账本亦不完整。因此那次历史审计**没有新跑**其精确 Van der Pol 和吞吐实验，不等于引擎运行 T10 失败。

保存的 Huan 修复版本在定点复查里通过若干矩阵、缩放和端点见证；Xiangru 的单独快照在若干严格局部输入上仍有精确值遗漏。原生 Flow* 是有完整时域数据的重要工程对照，也有其自身保存的标量仿射数值反例，不能当无条件真值裁判。我们的 CPU、范围请求、GPU 包裹与 resident 实现又各有自己的科学提交。作者、修复和许可应按版本与代码证据归属，不凭审计结果推断个人动机。本分支没有复制外部引擎、私人文件或证明 PDF；另一个“整套 GPU 引擎可行性／采用”任务已明确推迟。

目前最需要与 Xiangru 和 Huan 讨论三个具体问题。第一，怎样规定共同的观察**和内部验证**合同，才足以把当前保存对象的宽度比较推进到严格控制的算法比较？第二，哪些保留系数和接受／拒绝状态更新入口必须先完成证明账本，才可不加“局部”限定地称求解器严格？第三，单独 resident 块快而整段在线只有约 1.14–1.16 倍、仍远慢于匹配 Flow*，下一步应重画哪条 CPU/GPU 边界？[决策和待讨论问题](DECISIONS_AND_OPEN_QUESTIONS.md)记录证据支持到哪里。[单一实验目录](EXPERIMENTS.md)及[复现说明](REPRODUCING.md)让合作者先读已有表和图，再选择短例或完整运行；旧负结果及被替代材料有[确切恢复索引](../archive/index.csv)。
