## Fixed official contract

- [AINNCS 2026 report](https://easychair.org/publications/paper/GsKW/download), section 3.11, printed pages 98–99 (PDF pages 14–15): four physical states, 0.2 s sampled control, horizon 6 s, obstacle avoidance throughout `[0,6]`, and goal membership at `t=6`. Section 4 reports the CROWN-Reach partitions `40×16×1×1` for standard and `5×5×1×1` for robust (printed page 113, PDF page 29). Reading copy: `/Users/shengenli/Documents/ChatGPT/verification/output/flowstar_latest_20260930/reference/ARCH_COMP26_AINNCS.pdf`.
- [NAV instance README](https://github.com/Kiguli/ARCH-COMP2026/blob/d55dcc39f6496720adbf8ffdb7ff8c6e04bb8f26/benchmarks/NAV/README.md): initial `x1,x2∈[2.9,3.1]`, `x3=x4=0`; 30 periods of 0.2 s; avoid `x1,x2∈[1,2]` for the full time tube; reach `x1,x2∈[-0.5,0.5]` at `t=6`. The standard controller is `nn-nav-point.onnx`; the robust controller is `nn-nav-set.onnx`.
- [NAV repository dynamics](https://github.com/Kiguli/ARCH-COMP2026/blob/d55dcc39f6496720adbf8ffdb7ff8c6e04bb8f26/benchmarks/NAV/dynamics.m): `dx=[x(3)*cos(x(4)); x(3)*sin(x(4)); u(1); u(2)]`. Thus a direct four-coordinate execution uses `x1'=x3 cos(x4)`, `x2'=x3 sin(x4)`, `x3'=u1`, `x4'=u2`. The saved historical Flow* sources add only `t'=1`, `u1'=0`, `u2'=0` for sampled hold.

The paper prose names the states in this sequence: horizontal position `x`, vertical position `y`, angle `θ`, velocity `ν`. Its equation (15) displays the derivative vector `(ν cos θ, ν sin θ, u1, u2)`. If the prose sequence is also the vector order, `u1` is angle rate and `u2` is velocity rate. The repository dynamics instead uses its third coordinate as the speed multiplier and fourth as the heading, making the direct effective order `(x,y,ν,θ)` and giving `u1` the speed-rate role. The paper does not separately label the rows of equation (15), so this is a paper-prose versus executable-source semantic conflict rather than proof of the authors' intended controller axis order. Both initially zero coordinates make the initial set unable to resolve it.

## Controller file inspection

The fixed official point and set ONNX files were copied to local `results/archcomp26_20261001/official_nn-nav-{point,set}.onnx` and to the server's isolated `runs/archcomp26_20261001/nav_prep_001/` directory. Direct ONNX graph inspection in the server environment showed for **each** network `float32 [N,4] → float32 [N,2]`, nodes `MatMul, Add, Relu, MatMul, Add, Relu, MatMul, Add, Tanh`, and affine parameter shapes `4×64`, `64×32`, `32×2` with corresponding biases. Neither graph contains a preprocessing or axis-permutation node; generic tensor names `input` and `layer` do not encode physical axes. The report says **two 64-neuron hidden layers**; the supplied ONNX graphs have hidden widths **64 and 32**. The executable model architecture therefore differs from that paper description.

The server's historical `ARCH-COMP2024/benchmarks/NAV/networks/nn-nav-{point,set}.onnx` files and these fixed 2026 files compared byte-for-byte equal using direct file comparison, without calculating a digest. This establishes exact model-file identity for the historical runs, but not the physical meaning of each input or output axis.

The fixed 2026 official NAV directory contains only `README.md`, `dynamics.m`, and a `networks/` directory containing point/set `.onnx` and `.mat` files. A recursive listing of the fixed repository found no NAV training, conversion, or execution script that maps tensor columns to the named physical states or controller outputs. The paper's general controller description likewise says only that all states are inputs and `u∈[-1,1]^2` is the output. The missing evidence is an authoritative controller training/export or participant execution source that names the **four input columns and two output columns** for these exact point/set model files. Without that, the report-style `(x,y,θ,ν)` and repository-style `(x,y,ν,θ)` network interpretations cannot be identified from the ONNX graph.

## Saved execution mapping and existing state

The archived GPU standard/robust configs at `research/gpu_verified_20260930/report/configs/arch_nav_{standard,robust}.yaml` feed `(x1,x2,x3,x4)` to the corresponding point/set ONNX and implement the repository equations above, plus the three hold/clock derivatives. Both use 30 control periods, 0.2 s period, Flow* fixed step 0.01, order 4, and the correct full-time obstacle plus endpoint goal constraints. Standard uses `40×16=640` initial boxes; robust uses `5×5=25`. The archived native `results/archcomp_review_20260923/evidence_v2/suite_build/archcomp/nav_{standard,robust}/matched_threads4.cpp` uses the same repository equations, partition, and point/set network choice. Its checker examines the union of recorded ranges for obstacle unsafety and its end-of-time flowpipe for target membership, but needs an explicit completed-horizon guard before a new run may treat its verdict as final.

A future *new* standard native attempt may address its incomplete historical prefix, but it needs a fresh directory, correct point model, matched RPC port, completion guard, all-time obstacle checker, and a budget informed by the previous 300 s prefix (at least ~900 s for comparable throughput, with a larger operational limit).
